## 1. 文档目标与后端边界

### 1.1 服务目标

后端是 Ballance 比赛控制台的唯一业务状态源，负责：

- 启动、管理并监控 `BallanceMMOMockClient.exe`。
- 安全发送命令并根据服务器回显确认结果。
- 只读解析工作模式实时输出，以及测试模式的静态或增长日志。
- 维护比赛状态机、自动调度、阻断和事故处理。
- 管理玩家身份、轮次尝试、SR/HS 成绩、计分和人工覆盖。
- 向前端提供 HTTP 查询/动作接口和 WebSocket 实时事件。
- 使用 SQLite 和文件系统持久化比赛、事件、审计、导出与归档。

### 1.2 已确认决策

| 项目 | 决策 |
| --- | --- |
| 部署 | Windows 本机服务，固定监听 `127.0.0.1:32113` |
| 自动化权限 | 正常规则流程可全自动，包括正常 Go |
| 关键介入 | 手动 Go、重赛本关、已结算成绩修改等必须由前端取得确认令牌 |
| 默认比赛 | 原版关卡 SR 1–13 |
| 默认比赛类型 | 小型 |
| 默认服务器 | `1.bmmo.win`；另有 `0.bmmo.win`、`2.bmmo.win` 预设，均不附加端口 |
| 服务器控制身份 | 固定 `ContestConsole`，不可配置 |
| 正式系统裁判来源 | 仅本机托管 MockClient 的自身连接 ID |
| 运行模式 | 仅 `work` 工作模式和 `test` 测试模式；模式在发布后不可切换 |
| 测试安全 | 测试模式源文件只读，不启动真实 MockClient、不联网、不发送真实命令 |

### 1.3 明确不做

- 不修改 BallanceMMO 协议、服务端、MockClient 或游戏客户端。
- 不尝试向一个非本服务启动的 MockClient 进程注入控制台输入。
- 不自动裁决录像证据、代打、主观恶意和需要赛后调查的违规。
- 不直接集成腾讯文档私有 API。
- 不在首版提供云端账号、远程控制和多人实时写入。
- 不提供正式观察直播或独立回放模式；增长日志和播放能力统一属于测试模式。
- 不实现多裁判仲裁或运行中控制权交接；其他客户端发出的 Go 只记录，不驱动正式状态机。

## 2. 总体架构

### 2.1 组件

```text
前端浏览器
  └─ HTTP + WebSocket
        │
本机服务
  ├─ API 与本机会话
  ├─ 比赛状态机 / 自动调度器 / 事故管理
  ├─ MockClient 进程与命令适配器
  ├─ 日志读取器 / 解析器 / 标准事件总线
  ├─ 玩家身份 / 计分 / 人工覆盖
  ├─ 测试场景与日志播放引擎
  └─ SQLite / 原始日志 / 导出 / 归档
        │
BallanceMMOMockClient.exe ── BallanceMMO 服务器
```

### 2.2 推荐技术基线

- Node.js LTS + TypeScript。
- HTTP/WebSocket 框架需支持类型化输入校验、长连接和优雅停机。
- SQLite 作为嵌入式数据库，所有比赛写操作使用事务。
- 使用 Node 子进程管道管理 MockClient；若 Windows 控制台输入不兼容管道，替换为 ConPTY/node-pty 适配器。
- MockClient 适配器、比赛领域、解析器和存储之间使用接口隔离，不能让原始控制台命令渗透为业务模型。

当前服务端模块边界如下：

- `CompetitionService` 是 HTTP/API 门面，组合比赛生命周期、确认令牌、动作矩阵和快照，不直接拥有工作或测试运行时 Map。
- `WorkRuntimeManager` 独占真实 MockClient 生命周期、同服租约、命令队列、日志接收、名单对账和单调时钟驱动。
- `TestRuntimeManager` 独占场景目录、虚拟时钟、行为玩家、故障计划、测试日志和运行恢复。
- `ScoreboardService` 负责固定榜单版本、逐关修订权限、人工修订和覆盖审计；`RefereeActionService` 负责裁判动作执行与最末端命令编码。
- `CompetitionAuditService` 统一持久化原始日志、命令审计和注意事项。模块只能通过显式端口访问配置、SQLite、日志和事件，不得互读其他模块的私有运行 Map。

### 2.3 服务启动

- 固定绑定 `127.0.0.1:32113`，不得在端口占用时自动换用随机端口。
- 每次启动生成随机本机会话令牌，通过首次打开的本地 URL 交给前端。
- 检查数据库迁移、应用数据目录权限、MockClient 路径和可执行文件版本。
- 恢复未结束比赛时，不自动续发命令；先恢复状态并保持自动化暂停。
- 若上次退出发生在倒计时或比赛中，创建恢复事故并要求裁判确认现场状态。

### 2.4 开发实例替换

开发启动器必须保证更新后的后端启动前，旧开发实例已经停止：

1. 探测 `http://127.0.0.1:32113` 的实例信息接口，校验项目签名、工作区标识、实例 ID、版本和 PID。
2. 若确认是本项目旧开发实例，先调用受保护的优雅停止接口，停止接收新动作、提交数据库事务并关闭 MockClient/日志句柄。
3. 在限定时间内等待端口释放；仍未退出时，再校验 PID、进程启动命令和工作区路径，确认无误后终止旧进程。
4. 若端口由其他程序或无法验证身份的进程占用，不得擅自结束该进程；新后端启动失败并报告占用信息。
5. PID 文件仅作为线索，不能单独作为结束进程的依据，防止 PID 被复用后误杀其他程序。

生产环境的重复启动不强制替换正在工作的实例；应复用现有服务并打开前端。

## 3. 工作模式、测试模式与 MockClient 适配

### 3.1 工作模式

工作模式用于正式比赛。服务启动专用 MockClient 子进程并持有输入、输出和日志文件，可执行完整控制；不允许改为只读跟随外部日志。

默认启动参数语义：

- `-s <服务器地址>`：`bmmo.win` 系列预设只传主机名，例如 `1.bmmo.win`，不附加端口；自定义服务器可按需要包含端口。
- `-n <旁观登录名>`：最末端固定传入 `*ContestConsole`；配置、旧数据和探针参数均不得覆盖，也不得关闭旁观标记。
- `-u <UUID>`：固定 UUID，首次生成后持久化。
- `-l <独立日志路径>` 和 `--auto-flush`：保证实时日志。
- `--no-sound-files`：避免无关声音文件写入比赛目录。

启动参数使用数组传递，不通过 shell 字符串拼接。工作目录、日志路径和 UUID 文件必须按比赛隔离或明确管理。

### 3.2 测试模式

测试模式用于开发验证、裁判演练和历史材料分析，支持三种输入：

- `simulation`：假 MockClient、虚拟时钟、可编排命令回显和随场景按阶段触发的故障计划。
- `static-log`：只读打开完整日志，支持播放、暂停、倍速、逐事件、重置和跳转到下一次 Go。
- `growing-log`：只读增量跟随仍在增长的日志，用于验证实时解析。

测试模式不得启动真实 MockClient、连接 BallanceMMO 服务器或写入真实命令。测试动作由模拟命令发送器处理，并明确标为模拟结果。输入日志始终只读，数据库、缓存、导出和归档写入独立测试目录。

比赛模式在创建时确定；发布后不可切换。测试比赛可以复制为新的工作模式草稿，但只复制配置，不复制事件、成绩、事故、命令或测试状态。

### 3.3 能力模型

API 必须返回 `CompetitionMode` 和结构化 `Capabilities`，至少包含真实进程、联网、真实命令、自动化、虚拟时钟、日志播放和故障场景能力。工作模式调用测试接口、测试模式调用真实控制接口时统一返回“能力不支持”。

### 3.4 进程生命周期

- 启动后捕获标准输出、标准错误和退出码，并同时跟随 `-l` 日志。
- 识别连接成功、版本不兼容、登录拒绝、权限变化、断线和退出。
- 服务停止时先发送 `stop` 并等待正常退出；超时后仅在收到高风险确认后强制终止。
- MockClient 意外退出时立即阻断自动化，保存最后输出，不能静默重启正在比赛的控制进程。
- 重连操作只有在连接线程已结束且现场状态明确时执行。

### 3.5 版本兼容

- 启动时运行或读取 MockClient 版本并保存到比赛运行记录。
- 未验证版本可进入观察状态，但裁判确认前不得启用自动控制。
- 命令和输出格式差异封装为版本化适配器；业务状态机不得依赖散落的正则或命令字符串。

## 4. 比赛配置与校验

### 4.1 基本配置

| 配置项 | 默认值/规则 |
| --- | --- |
| 比赛名称 | 必填，用于页面、导出和归档目录 |
| 比赛日期与时区 | 本机日期、`Asia/Shanghai`；可修改 |
| 服务器控制身份 | 固定 `ContestConsole`；MockClient 登录名固定为 `*ContestConsole` |
| MockClient UUID | 首次生成后固定；比赛中不可更换 |
| 服务器 | `1.bmmo.win`；三个 `bmmo.win` 预设不附加端口，自定义地址可包含端口 |
| 比赛类型 | 默认小型，也可选择大型、自定义 |
| 参赛策略 | 无需预登记；根据普通玩家的 login、disconnect 和 `list` 列表自动登记，`*` 开头的旁观者排除 |
| 排行榜显示名 | 可选的“游戏内玩家 ID → 显示名”映射，只影响榜单和导出显示 |
| 归档位置 | 应用数据目录下按比赛 ID 隔离，可选择合法外部目录 |

### 4.2 轮次模型

每轮至少包含：

- 稳定轮次 ID、顺序、`mapKind: official | custom` 和显示名称。
- 官图使用 `level 0..13`，显示名称从模式和关卡号派生为 `SR1`、`HS1`，命令目标统一编码为 `level N`。
- 自制图保存完整 32 位 MD5 与通知/榜单显示名称，内部发令关卡号固定且隐藏为 `0`，命令目标编码为 `<完整哈希> 0`。
- 模式：SR 或 HS，各轮独立，允许混合。
- 限时：默认 10 分钟；SR13、HS12、HS13 默认 15 分钟。
- 预计准备时间、公告提前量、Ready 缓冲和轮间间隔。
- 计分方案、是否计入总榜、迟到策略和提前结束条件。
- “最后计分名次”、达到该名次后的默认休息时间和上一轮成绩接收截止策略。

提供 SR 1–13、HS 1–13 和空白模板。轮次顺序变更必须使用稳定 ID，不能靠数组下标关联历史结果。读取缺少 `mapKind` 的旧配置时按官图迁移；已发布的不可变配置载荷不得因读取迁移而原地重写。

### 4.3 计分配置

内置：

- 小型：`20, 15, 12, 10, 8, 6, 5, 4, 3, 2, 1, 1`，第 13 名起为 0 分。
- 大型：`30, 24, 21, 18, 16, 14, 12, 10, 8, 6, 5, 4, 3, 2, 1`。
- “最后计分名次”由计分表最后一个非零得分自动推导，小型为 12、大型为 15；该名次之后、DNF 和排除结果默认 0 分。

支持逐名次自定义、最后计分名次、尾部统一分数和单轮覆盖。得分必须是有限数；负分作为比赛级开关，默认不允许。

### 4.4 流程策略默认值

- 公告提前量：5 分钟。
- 单次延时上限：5 分钟。
- 重连稳定窗口：15 秒；延时相关玩家全部连续在线达到该窗口后可提前结束延时。
- 自动发令固定节奏：三次 Ready 间隔 5 秒，`READY!` 与 cheat off 继续各间隔至少 5 秒，cheat off 真实确认后至少等待 10 秒。
- 起跑保护窗口：Go 后 15 秒。
- 赛前掉线：自动暂停并等待重连。
- 赛中单人掉线：继续比赛并记录。
- 群体异常阈值：2 人或参赛者的 20%，取较小的非零值。
- 达到最后计分名次：立即按默认 3 分钟轮间休息安排并通知下一轮 Ready，不等待本关剩余时限；该名次之后的完赛或 DNF 不改变后续流程计划。
- 上一轮成绩接收截止：下一轮实际进入 Ready 或上一轮关卡时限，以先到者为准。Ready 被阻断时窗口继续开放，但不得越过时限。
- 关键命令：不自动重试；普通通知确认未发送时最多重试一次。

### 4.5 配置版本

- 草稿可自由编辑并形成增量版本。
- 发布生成不可变规则快照，自动流程只读取已发布版本。
- 已开始轮次的地图、模式、计分和流程策略不能直接覆盖；通过结构化审计的比赛修订生成新版本。
- 每个结果、命令、事件判断和导出关联其使用的配置版本。

### 4.6 发布校验

至少验证：服务器地址、日期时区、控制身份、轮次顺序、地图 MD5、模式、限时、计分表、通知模板、显示名映射冲突、流程策略和归档路径；三个 `bmmo.win` 预设不得携带端口。参赛者名单为空不得阻止发布或启动。

## 5. 领域模型与玩家身份

### 5.1 核心数据对象

- `Competition`：比赛信息、服务器、发令员、状态和策略。
- `CompetitionConfigVersion`：已发布规则快照。
- `Stage`：地图、模式、顺序、限时、计分和通知计划。
- `ScoringScheme`：计分表和同分规则。
- `Participant`：贯穿比赛的稳定选手实体。
- `ConnectionIdentity`：一次服务器连接的 ID、名称和状态。
- `Attempt`：某轮一次权威 Go 创建的尝试。
- `ResultIntakeWindow`：一次尝试接收有效成绩的开始、截止和关闭原因。
- `RuntimeSnapshot`：用于中断恢复的比赛现场快照、下一动作和外部连接状态。
- `RawLogEvent`：原始行、文件、偏移、时间和哈希。
- `DomainEvent`：解析后的登录、Go、完赛、DNF、Warning 等事件。
- `StageResult` / `ScoreboardVersion`：计算结果及版本。
- `RankingBaseline`：当前轮第一名出现前锁定的上一轮累计排名，用于实时计算排名变化。
- `Override`：人工覆盖、原因、操作者和撤销关系。
- `CommandAudit`：动作、MockClient 命令、来源、确认和结果。
- `Incident`：证据、自动建议、裁判决定和处理状态。

### 5.2 连接、玩家 ID 与显示名

- “玩家 ID”指游戏内显示名称，例如 `Silent_Snow`，不是日志中的 `#123456` 数字连接 ID。
- 数字连接 ID 是一次连接的临时信息，只用于现场追踪和连接历史，不作为成绩归属键。
- 工作模式观察到普通玩家 login、disconnect 或 `list` 列表项时，按不区分大小写的游戏内玩家 ID 自动创建或更新稳定 `Participant`；有效完赛/DNF 可作为观察遗漏时的兜底。
- 名称以 `*` 开头的连接视为工作人员/旁观者，不自动登记为参赛者。
- MockClient 启动后 1 秒执行首次 `list`，之后在大厅、暂停或复核等安全阶段默认每 30 秒执行一次，以发现控制台启动前已在线或事件遗漏的玩家。解析器必须同时支持旧式 `N player(s) online` 列表头，以及实服逐客户端行后以 `N client(s) online: X player(s), Y spectator(s).` 收尾的格式；旁观者排除，末尾汇总可作为命令确认和整批对账边界。不得让对账命令阻塞 Ready/Go 等比赛命令。
- 游戏内玩家 ID 与排行榜显示名映射独立，例如 `Silent_Snow → 渴望新地图`。映射只改变榜单、导出和玩家页显示，不改变成绩归属、尝试、连接历史或计分哈希。
- 同一玩家 ID 的大小写变化归入同一实体并保留首次观察到的写法；真正改名、重名和黑白名单策略留给后续有审计的身份功能处理。

### 5.3 玩家状态

维护在线/离线、游戏内玩家 ID、数字连接历史、排行榜显示名、角色、cheat、地图、区段、Ping、最后事件、重连次数和本轮状态。

名称以 `*` 开头的连接默认归类为工作人员/旁观者，不自动登记为参赛者。

### 5.4 预留模型

显示名映射首版已实现；继续预留报名 ID、平台账号、白名单、黑名单、禁赛记录、工作人员角色和证据链接。后续控制是否允许登记时，不得改变游戏内玩家 ID 作为成绩归属键的语义。

## 6. 日志读取与标准事件

### 6.1 时间语义

- 实时调度使用服务端单调时钟，不能用系统墙上时间差值驱动 Go 或超时。
- 同时保存单调时间、墙上时间、时区和原始日志时间。
- 日志前缀 `[MM-DD HH:mm:ss]` 用于日志内排序，缺失年份使用比赛配置年份。
- 回放日志写入时间与通知文本中的计划时间可能不一致。Bulletin/Notice 内的 `HH:mm` 只作为文本，不修正事件时间。
- 关卡时限从权威 Go 事件开始，不从公告、Ready 或文件修改时间开始。

### 6.2 需要解析的格式

- 连接尝试、成功、断开、版本不兼容和登录拒绝。
- 初始在线列表、登录、掉线、踢出和客户端崩溃。
- 玩家 ID、名称、cheat、地图、区段和 Ping。
- Notice、Announcement、Bulletin、公共/私有聊天。
- Get ready、3、2、1、Go。
- 完赛：玩家、地图、模式、服务端名次、分数、用时和 cheat 标记。
- DNF：玩家、地图、最远区段和 cheat 标记。
- Warning、全局 cheat 切换、权限变化、操作拒绝和命令错误。

自制图未注册名称时使用服务端带引号的 `"哈希前缀.."` 回显，只能在完整配置哈希中做唯一前缀匹配；连接后执行 `setmap <MD5> 0 <地图名>` 时，Ready、Go、完赛和 DNF 会改为带引号的地图名，必须对已发布显示名做精确且唯一匹配。不唯一或不一致时仅保留原始日志，不归属成绩。官图在实服可能回显不带引号的哈希前缀，只能由当前裁判在当前权威关卡的 Ready/倒计时/Go 行建立临时绑定，不能把任意哈希回显直接归为官图。

未知行保存为 `RawLogEvent` 和 `UnknownDomainEvent`，不得导致解析线程崩溃或改变比赛状态。

### 6.3 增长文件读取

- 工作模式日志和测试模式 `growing-log` 输入支持增量读取；测试模式 `static-log` 使用完整、不会再增长的日志文件。
- 以允许其他进程继续写入的只读共享模式打开。
- 按字节偏移读取，仅在完整换行后解析，保留未完成尾行。
- 用文件标识、偏移和内容哈希去重。
- 检测文件截断、轮转和替换，不能把新旧文件偏移混合。
- 移除 ANSI 控制码后按 UTF-8 解析；异常字节保留原始数据并生成诊断事件。
- 原文件始终不写入、不截断、不重命名、不改变时间戳。

### 6.4 事件幂等与顺序

- 每个原始事件具有稳定来源 ID，可重复读取而不重复计分。
- 标准事件保留原始事件引用和解析器版本。
- 同一行产生多个领域事件时共享来源并具有确定顺序。
- 实时标准输出与日志文件出现相同内容时，适配器必须关联或去重，避免双计。
- 解析失败可在新版解析器中重建派生事件，但不能删除旧原始数据。

## 7. 正式尝试与比赛状态机

### 7.1 权威 Go

只有同时满足以下条件的 Go 才创建正式尝试：

- 工作模式中的发令来源为本机 MockClient 自身连接 ID；显示名称只用于界面和审计，不作为授权依据。
- 地图和模式与当前轮次一致。
- 当前状态允许进入比赛中。
- 事件未被识别为重复或已归属其他尝试。

正式系统以本机作为单一裁判，不接受其他客户端接管或代理发令。其他来源的 Go 保存为外部发令事件并进入未归属列表，不创建尝试。

测试模式没有本机真实连接 ID，但普通玩家行为场景不得提供或代理 Ready/Go。测试运行由裁判状态机生成模拟权威发令并驱动与工作模式相同的尝试边界；行为场景只声明玩家及其对当前比赛状态的反应。高级日志回放可以包含历史 Go，但必须标记为 `scripted-replay`，不得混入普通场景库，也不能放宽工作模式的单一裁判校验。

Go 前的同关完赛、DNF 和 Warning 属于练习/无关事件，不计入正式成绩。上一关窗口开放期间，已完赛玩家可能进入下一关练习：关卡与当前尝试不符的完赛、DNF、Warning 和 `[CHEAT]` 完赛只保留原始日志，直接跳过成绩、排除和注意事项处理；玩家已有当前关终态结果后出现的无关卡 cheat 切换也不得回溯排除当前成绩或阻断下一 Ready。其他确需裁判关联的错误模式、外部发令和已结束尝试记录进入未归属队列。

### 7.2 状态机

```text
草稿 → 已发布 → 大厅/练习 → 准备检查 → Ready → 倒计时 → 比赛中
                                              │             │
                                              └→ 事故/暂停 ←┘
比赛中 → 本轮结算 → 轮间准备 → 下一轮大厅/练习
比赛中/尾部接收 → 裁判重赛本关 → 旧尝试作废 → Ready
最后一轮结算 → 比赛复核（事务内转为已结束）→ 已归档
```

状态迁移使用数据库事务、当前状态版本和预期事件，拒绝过期动作。

### 7.3 自动化启用

裁判通过前端完成一次启用确认。后端检查：

- MockClient 已连接并具有权限，版本已确认。
- 服务器、登录身份、日期和时区正确。
- 轮次、计分和通知模板已发布；参赛者允许在运行中根据在线观察动态登记。
- 不存在身份冲突、上次事故或其他阻断。

首次启动后先按 `intermissionMs`（默认 3 分钟）安排首轮第一条 Ready，并立即发送 `关卡名 将在 HH:mm 发令` Bulletin。`HH:mm` 只按 UTC+8 计算，不显示日期或时区；下一 Ready 与 Bulletin 共用第一条 Get ready 的计划源。正常轮次的公告、Ready、关闭 cheat、倒计时和 Go 无需逐次人工确认。工作与测试运行必须由持续的 1× 单调时钟调度同一 `CompetitionController` 和同一流程策略；测试模式只替换玩家事件源、命令传输和故障适配器。虚拟时钟推进仅响应显式快进接口，不能作为测试模式默认自动跳时。

暂停或一般阻断只停止未来 Ready/Go 等发令，不停止单调时钟、当前成绩接收窗口或关卡时限；恢复自动化沿用暂停前阶段及既有计划，不重新插入首轮等待。存在未决 `uncertain`/`timed_out` 流程命令时，必须先逐条完成裁判处置，才允许恢复。

### 7.4 正常单轮流程

1. 第一条 Ready 前 60 秒发送 Notice：`某某关 1 分钟后即将发令，请提前做好重启游戏等准备，避免影响发令流程。`；字符串必须完整保留。
2. 到准备时间执行连接、参赛者、地图、模式和延时检查。
3. 在 T、T+5 秒、T+10 秒各发送一次 Get ready；每次都必须确认，且距上一次真实确认至少 5 秒，才能进入下一次。
4. 不早于 T+15 秒且距第三次 Ready 确认至少 5 秒发送 Announcement `READY!`；不早于 T+20 秒且距其确认至少 5 秒关闭全局 cheat；从 cheat off 真实确认再等待至少 10 秒且无阻断后继续。任一回显延迟时后续边界整体顺延。
5. 工作模式发送真实 countdown 并等待服务器依次回显 `3、2、1、Go`；测试模式以相同的一秒间隔生成这四个事件。
6. 只有权威 `Go` 到达后才创建 `Attempt`、进入比赛中并启动时限，`3/2/1` 不得提前创建尝试。
7. 接收完赛、DNF、Warning、掉线和崩溃事件，更新本轮和总榜。
8. 当前轮产生“最后计分名次”时，本轮进入“尾部成绩接收”，立即安排并通知默认 3 分钟后的下一轮 Ready，不等待本关剩余时限。后续结果不改变该计划；在窗口关闭前的完赛仍可作为零分名次记录。
9. 下一轮实际进入 Ready 时，原子关闭上一轮成绩接收窗口。此后出现的上一轮完赛保留原始事件并标记“截止后记录”，不进入成绩。
10. 到关卡时限时关闭窗口，并给尚未完赛者写入 `time-limit` DNF 结果；不得向 MockClient 日志伪造 `did not finish` 行。
11. 若参赛人数少于最后计分名次，或全部选手在该名次产生前已完赛/DNF，则在全部选手状态确定时安排下一轮。
12. 最后一轮没有下一轮 Ready，继续到全员完赛/DNF、关卡时限或裁判人工结束，再进入比赛复核。

写入 MockClient stdin 只代表命令已发送给进程，不能作为服务器执行成功。无回显时保持原业务状态。

命令队列必须先建立回显观察再写入 stdin。服务恢复 `sent` 命令时，若持久化的权威 Go 与正式尝试可以证明对应 Go 已执行，则恢复为 `acknowledged`；其余才转为 `uncertain`。精确权限失败反馈必须立即标记命令失败并阻断自动化。

工作 MockClient 首次连接成功后，按已发布关卡顺序一次性发送所有自制图名称映射 `setmap <完整32位MD5> 0 <地图名>`。同一运行内 Ready、重赛和手动发令不得重复注册。

“进入 Ready+发令流程”把计划目标关第一条 Ready 改为当前时间加 1 分钟，立即发布 Bulletin 与上述 Notice，并自动执行完整时间轴。尾部成绩接收期以已规划下一关为目标，第一条 Ready 实际进入时关闭旧窗口。

“手动 Ready”只向计划目标关发送一次 Ready；“关闭 cheat”只发送一次命令，并把成功回显作为绑定目标关的手动 Go 前置证据。二者都不改变阶段、计划时间、Bulletin 或自动步骤进度。手动 Go 不要求三次 Ready、`READY!` 或计划时间，但要求目标关已有 cheat off 确认、参赛者未显示 cheat、权限与连接正常且无未决命令；请求后停止该目标关未发送的自动步骤。只有权威 Go 才创建尝试，并用其真实时刻设置本关发令和最晚结束时间；无 Go 或结果不确定时不得提前计时。

### 7.5 自动阻断

以下情况阻止正常自动起跑：

- MockClient/服务器未连接、版本未确认或权限不足。
- 参赛者在 Ready 阶段掉线且仍处于等待期。
- 存在身份冲突、未处理延时或上一轮未决事故。
- 关闭 cheat 未确认或参赛者仍显示 cheat 开启。
- 当前轮次地图/模式不一致。
- 本机休眠/唤醒、系统时间异常、日志中断或自动化暂停。

阻断必须产生结构化原因、严重度、是否可自动恢复和建议动作，通过 WebSocket 推送。

运行时同时维护并持久化“流程动态与注意事项”：包含流程里程碑、下一 Ready 规划、成绩窗口、违规排除、阻断、事故和不确定命令。API 返回中文标题、摘要、严重度、时间和关联对象，前端不得直接展示内部 JSON。

### 7.6 定时与系统休眠

- 调度器使用单调时钟和持久化的计划动作。
- 进程休眠/唤醒或事件循环延迟超过阈值时，不补发已过期 Go；进入阻断并重新检查。
- 普通过期公告可根据策略跳过或立即发送，但必须记录。
- 前端断开不影响调度，后端进程停止则不得由浏览器计时补偿。

### 7.7 成绩接收窗口

- 权威 Go 创建尝试时同时打开 `ResultIntakeWindow`。
- 达到最后计分名次只触发下一轮调度，不关闭窗口，也不作废其后名次的有效记录。
- 下一轮因掉线、延时或其他阻断未实际进入 Ready 时，窗口保持开放，但不得越过本轮关卡时限。
- 下一轮从准备检查真正迁移到 Ready 的同一事务中，先关闭上一轮窗口，再发送本轮 Ready 相关动作，避免边界竞态。
- 截止点附近事件按后端收到并持久化的标准事件顺序判定；恰好在关闭事件之前的完赛有效，之后无效。
- 截止后的记录继续进入原始/标准事件存储和审计，但不能修改上一轮成绩。

## 8. 掉线、崩溃与重赛

### 8.1 Go 之前

- 参赛者在 Ready 或计划倒计时前掉线：暂停起跑、发送等待通知并开始延时。
- 玩家在上限内重连且身份关联成功：为该玩家启动连续在线稳定计时，默认 15 秒；期间再次掉线则清零重计。
- 所有导致延时的玩家均达到稳定窗口，且不存在其他阻断时，提前结束延时并重新执行准备检查和 Ready，不从中断倒计时续发。
- 达到上限仍未重连：按已发布迟到策略处理为缺席或允许迟到，不临时猜测。
- MockClient 自身断线：立即阻断；恢复后重新检查，不能补发不确定的 Go。

### 8.2 Go 之后

- 单个玩家普通掉线：记录，默认继续本轮，允许依规则重连。
- 起跑保护窗口内出现明确崩溃，或掉线达到群体阈值：创建 `Incident`、暂停后续自动动作并建议重赛。
- 超出保护窗口的单人掉线不自动建议重赛，裁判可手动升级。
- MockClient/服务器整体断线：暂停自动结算，保留已收到事件，等待恢复或裁判处理。

### 8.3 重赛事务

“重赛本关”在当前关已有权威 Go、且下一关尚未进入 Ready 时可用，不要求先创建事故。动作必须使用前端取得的短时确认令牌，令牌绑定比赛、轮次、当前有效尝试、状态版本和影响摘要；事故仅作为可选证据保留。

确认后按一个业务事务处理：

1. 当前尝试标记“作废待重赛”，其成绩从有效总榜移除，原始事件和结果不删除。
2. 保存裁判、结构化原因、可选事故证据和确认摘要。
3. 发送重赛通知并返回 Ready 流程。
4. 在下一次倒计时前一次性执行 `forcenextrestart`。
5. 新权威 Go 创建新尝试；Go 回显前不认为重赛开始。

`forcenextrestart` 和 Go 不自动重试。若发送或回显状态不确定，进入阻断并等待裁判恢复。确认重赛后重新进入的正常 Go 无需再次确认。

### 8.4 DNF、排除与 Warning

- 正式尝试内收到对应地图的 DNF，立即标记选手本轮 DNF。
- 关卡时限到达后，状态机为仍未完成的参赛者生成 `time-limit` DNF 结果；该结果只写业务状态和流程动态，不伪造 MockClient DNF 日志。
- 可识别玩家和关卡的两类明确非法 Warning 标记为 `excluded`，自动记 0 分并保留原文；无法定位玩家或关卡的 Warning 只进入注意事项。
- Warning 后的真实完赛保留作证据但不恢复计分。
- 模糊 Warning、申诉和录像证据进入待复核，不自动扩展处罚。
- 裁判可在成绩页将结果设置为有效名次或 DNF；覆盖生成新版本并保留原事件。

### 8.5 比赛中开启 cheat

- 正式 Go 后，尚未有效完赛或 DNF 的参赛者个人 cheat 状态从关闭变为开启时，立即将该玩家本轮标为 `excluded`，创建高优先级注意事项并推送前端。
- 判定窗口从权威 Go 开始，到该玩家有效完赛/DNF或本轮成绩接收窗口关闭为止。
- Go 前的练习阶段允许玩家开启 cheat，不创建排除或处罚事件。
- 玩家已经有效完赛/DNF 后、下一轮 Ready 前再开启 cheat，视为下一关练习日志：不追溯改变该轮成绩，也不把该行形成下一 Ready 阻断；下一轮 Ready 流程仍会统一关闭 cheat。
- Ready 阶段发现玩家 cheat 开启时阻断 Go 并要求关闭；若权威 Go 到达时仍为开启状态，按本轮排除报告。
- 裁判发出的全局 cheat 开启事件视为比赛事故，不批量排除所有选手，等待裁判处理。
- 自动排除报告保存触发事件、玩家、尝试、cheat 前后状态和时间；后续真实完赛保留作证据，但不得伪造 DNF 日志。

## 9. 命令队列与审计

### 9.1 业务动作

API 接收类型化动作，例如发送 `bulletin | notice | announce`、进入 Ready+发令流程、手动 Ready、关闭 cheat、手动发令、Ready 改期、关卡时限改期、结束轮次、重赛、kick。玩家处置公开入口只保留 kick 和高级原始命令，只有后者接收受限文本。

业务层负责把动作转换为版本适配器命令，前端不得提交可执行 shell 字符串。

### 9.2 命令状态

命令状态至少包括：

`queued → sent → acknowledged | failed | timed_out | uncertain`

- `sent` 仅表示写入 MockClient。
- `acknowledged` 需要匹配服务器回显或明确响应。
- 超时但可能已经执行的不可幂等命令进入 `uncertain`，不能自动重试。自动流程的查询和通知使用 10 秒确认窗口，Go 使用 15 秒确认窗口。
- 每条未决流程命令向裁判提供“确认已执行”和“执行重发”两个结构化动作；两者都绑定比赛版本、原动作、影响哈希和短时令牌。
- “确认已执行”只把运行时动作标记为裁判已核对，不发送命令；“执行重发”由裁判显式触发一条新命令并等待新回显。两种处置都保留原 `uncertain`/`timed_out` 命令审计，重发记录使用新的审计 ID，绝不覆盖或伪装成自动重试。
- 查询和普通通知只有在可证明未发送时才允许一次重试。

### 9.3 串行与幂等

- 同一比赛的竞赛命令串行执行。
- API 动作携带幂等键；重复提交返回原动作结果。
- 动作携带期望状态版本，不匹配时拒绝执行。
- 命令审计保存业务动作、实际命令、参数、来源（自动/手动）、操作者、确认令牌摘要、时间和回显。

### 9.4 确认等级

| 等级 | 示例 | 后端要求 |
| --- | --- | --- |
| 自动安全 | 计划公告、查询、自动 Ready、自动关闭 cheat | 自动化已启用且状态允许 |
| 自动竞赛 | 正常倒计时和 Go | 自动化已启用、所有阻断通过 |
| 手动重要 | 进入 Ready+发令流程、改期、延长时限、提前结束、手动 Go | 有效确认摘要和当前状态版本 |
| 关键介入 | 重赛本关、修改已结算名次 | 有效确认令牌、目标、影响哈希和结构化审计 |
| 高风险管理 | kick、原始命令、强制结束进程 | 高风险确认令牌；原始命令功能已启用 |

所有需要确认的动作都由按钮旁的内联面板完成。后端确认摘要至少包含目标、当前阶段、状态版本、具体影响和令牌有效期；状态或目标变化后令牌失效。普通裁判操作不接收自由文本原因，审计原因由动作、目标和影响结构化生成。

## 10. 计分与人工覆盖

### 10.1 单轮成绩

- SR 按服务器有效完赛顺序排名。
- HS 按最终有效分数从高到低排名，分数相同时按完赛顺序。
- 保存原始服务端名次、分数、用时、生命、连接 ID、尝试号和事件来源；成绩按“关卡 + 尝试”归档，不以关卡号覆盖旧尝试。
- 每关榜单只读取最新有效尝试；已作废尝试及其原始证据永久保留，但不进入有效榜。未归属事件同样不进入有效榜。
- cheat、明确 Warning 和带 `[CHEAT]` 的完赛标为 `excluded`，保留原始/后续完赛证据、自动记 0 分并让其他选手顺延；不会借此生成 DNF 日志。
- 未参加、超时、主动 DNF 和成绩页裁判判定显示 DNF，并保留原因代码。

### 10.2 总榜与同分

总分为所有计分轮次得分之和。总分相同时依次比较第一名次数、第二名次数、第三名次数，直至所有可比较名次；完全相同则并列。DNF 和未参赛不参与名次次数比较。

排行榜必须随比赛事件实时更新，而非等待关卡结束：

1. 每条归属于有效尝试、且处于成绩接收窗口内的完赛或 DNF 都触发一次完整重算并生成新的 `ScoreboardVersion`。
2. 即使 DNF 未改变得分或总排名，也必须生成新版本，以反映玩家状态、事件序号和更新时间。
3. 当前轮首个有效完赛事件到达时，在应用该完赛结果前创建 `RankingBaseline`，保存上一轮累计榜中每名选手的排名。
4. 应用首个及后续完赛/DNF 后，以 `基线排名 - 当前排名` 计算变化：正数显示上升，负数显示下降，零为不变。
5. `RankingBaseline` 在本轮内不可变；后续人工修订会更新当前榜单，但不重写已锁定基线。
6. 当前轮第一名出现前不创建新基线，排名变化按不变处理；第一轮没有上一轮基线，排名变化为空。
7. 截止后记录、练习记录、未归属事件和已作废尝试不生成有效榜单版本。

每个 `ScoreboardVersion` 包含触发事件、输入事件版本、配置版本、基线 ID、完整排名、变化值和确定性哈希。尝试作废或人工覆盖也立即生成新版本并通过 WebSocket 推送；人工修订与后续自动成绩共用同一个单调版本序列，禁止版本碰撞或互相覆盖。

### 10.3 人工覆盖

成绩页只接受“玩家 + 轮次 + 设置名次”或“玩家 + 轮次 + 设置 DNF”修订，允许对空成绩设置 DNF，也允许把空成绩直接补成有名次结果。比赛运行时仅允许修订当前关之前、且已进入下一关 Ready 的关卡；`finished` 或 `archived` 后允许修订全部关卡。后端必须在签发确认和最终写入两个入口重复校验该权限，不能依赖前端禁用状态。后端拒绝直接提交单关得分、总分或显示名；目标及受顺延影响结果的得分必须按该轮配置自动重算。覆盖保存：

- 修改前/后值、操作者、时间和结构化动作原因。
- 关联原始事件或证据说明。
- 引发的重新排名和得分差异。
- 撤销关系。

覆盖层不修改原始事件。当前界面在修订名次或 DNF 时都提供“其他玩家是否顺延”确认项，顺延时要在确认内容中列出受影响玩家；不顺延时直接按当前规则计分，不要求检查同名次、排名连续等额外约束。重算必须从修订前的完整玩家集合开始，不能只返回被改玩家和受影响片段，且刷新快照、WebSocket 更新和重启恢复后人数必须保持一致。撤销覆盖入口尚未实现；选手归属和是否计入总榜等复核继续作为后续独立审计动作，不能通过成绩页手填得分变相实现。

### 10.4 导出数据

- 建立共享成绩表模型：`变化｜名次｜总分｜选手｜每关独立列`。前端页面、剪贴板 HTML/TSV、CSV 和 XLSX 必须使用同一行列与单元格文本，不把轮次结果合并成单一字段。
- 下载接口只接受 `xlsx | csv`；HTML/TSV 仅由前端从共享模型生成用于剪贴板，不提供下载端点或归档文件。
- XLSX 保留冻结表头、每关前三名颜色、DNF 删除线、排除样式和固定榜单版本；CSV 带 BOM 并正确转义。
- 当前实时版、指定固定版本和最终复核版都由版本参数固定；文件名含比赛名、工作/测试模式、版本和导出时间，XLSX 工作表名同样标识模式。

## 11. HTTP 与 WebSocket 接口

### 11.1 HTTP 资源

按以下资源组织：

- 健康与兼容性：服务、数据库、MockClient 版本、进程、连接、权限和日志状态。
- 比赛：列表、新建、复制、更新草稿、发布、启用/暂停自动化、结束、归档和删除；新建默认 `work`，删除在任何状态都允许，但必须先中止运行并要求版本、幂等键、影响哈希和确认令牌。

- 工作模式允许多个比赛并行运行，但规范化后的同一服务器地址同一时刻只能存在一个工作运行；比较时忽略主机名大小写、首尾空白和末尾点号，并规范化端口数字。命中冲突时返回结构化冲突信息。
- 轮次与尝试：快照、改期、延长、结束、事故、重赛确认。
- 玩家：在线连接、参赛者、身份关联、角色和备注。
- 成绩：单轮、总榜、覆盖、撤销、复制数据和导出。
- 事件：原始/标准事件分页查询及过滤。
- 动作：通知、流程控制和高风险管理命令。
- 测试运行：创建场景、打开静态/增长日志、播放、暂停、调速、逐事件、跳转和重置；普通场景的故障由场景计划驱动，不公开手动故障注入动作。

接口输入必须进行运行时校验。错误响应至少区分验证失败、能力不支持、状态冲突、确认失效、命令失败和内部错误。

### 11.2 写动作公共字段

每个写动作包含：

- 比赛 ID。
- 期望状态版本。
- 客户端幂等键。
- 来源和操作者。
- 需要时的确认令牌和影响哈希。

成功响应返回新状态版本、动作 ID 和命令 ID；异步结果通过查询和 WebSocket 更新。

### 11.3 WebSocket 事件

至少推送：

- 进程、连接、权限和日志健康状态。
- 新原始日志和标准化事件。
- 比赛状态版本、权威计时和下一动作。
- 玩家状态和身份冲突。
- 单轮成绩、总榜版本和覆盖。
- 命令状态。
- 阻断、事故和待裁判决定事项。

每个事件带全局或比赛内单调序号。客户端重连可从序号续传；超出保留范围时要求重新获取快照。

每条有效完赛或 DNF 处理完成后必须推送对应的 `ScoreboardVersion`；不得合并到关卡结束才推送。短时间内连续事件可以压缩网络传输，但客户端仍须能按版本序号取得每个中间榜单。

### 11.4 本机会话

- 首次启动生成随机会话令牌，令牌只允许访问本机 API。
- 写请求防止来自任意网页的跨站调用，校验 Origin/令牌并限制 CORS。
- 支持一个活动控制会话；其他页面默认只读，控制权变更写入审计。

## 12. 持久化与归档

### 12.1 持久化原则

- 原始事件、命令审计、事故和人工覆盖只追加，不原地篡改。
- 派生比赛状态和榜单可从规则快照、原始事件及覆盖重建。
- 每个完整原始事件先落库，再在同一处理链中事务性保存标准事件和状态变化；不能只在关卡结束保存。
- 状态版本、事件序号和命令队列在同一业务事务内保持一致。
- 每次状态迁移、命令状态变化、成绩更新和事故处理后更新 `RuntimeSnapshot`；比赛中另做短周期检查点，确保随时可恢复现场。
- SQLite 启用 WAL 和适合关键现场数据的同步级别；关键 Go、重赛、成绩接收窗口关闭和人工覆盖提交后必须确认数据已持久化。
- MockClient 文本日志保持自动刷新，应用日志和数据库不得共用一个可能同时损坏的文件。
- 数据库迁移有版本号、备份和失败回滚策略。

### 12.2 文件布局

每场比赛使用独立目录，至少分为：

- `logs/`：MockClient 文本日志和应用运行日志。
- `records/`：可选二进制记录。
- `exports/`：仅 XLSX、CSV。
- `archive/`：归档清单和最终包。
- 数据库保存规范化元数据和文件相对引用。

实际目录名需安全清理，不能直接把比赛名称作为未经处理的路径。

### 12.3 归档内容

归档包至少包含：

- 原始 MockClient 文本日志和 SHA-256。
- 可选二进制记录及 SHA-256。
- 比赛配置版本、轮次、计分、自动登记参赛者、数字连接历史和显示名映射快照。
- 标准化事件、命令审计、事故和人工覆盖。
- 每轮结果、最终总榜及 XLSX/CSV。
- 应用版本、解析器版本、MockClient 版本、时区和归档清单。

归档先生成清单并校验文件，成功后标记只读。重新复核创建新的复核版本和归档，不覆盖原包。

比赛状态迁移到“复核”时，必须在状态迁移事务内立即持久化为 `finished`、停止运行并开放全部关卡修订；读取快照不得承担改变比赛状态的隐式副作用。草稿、已发布运行中、已结束和已归档比赛均可通过高风险确认直接删除，删除前先停止对应运行并释放同服租约；独立归档包不随比赛记录删除。

### 12.4 崩溃恢复

- 服务启动后从规则快照、事件流和最后 `RuntimeSnapshot` 重建原比赛现场，不创建新比赛、不清空尝试或重新编号。
- `sent` 但未确认的不可幂等命令恢复为 `uncertain`；裁判逐条选择“确认已执行”或“执行重发”，原审计记录不变。
- 若比赛处于 Ready、倒计时、比赛中、尾部成绩接收或事故，先恢复对应状态并保持自动化暂停。
- 原始日志读取从最后已提交偏移继续，并通过哈希避免重复。
- 使用同一比赛服务器、裁判配置和固定 UUID 重新启动 MockClient 并重连；保存新的进程/日志分段，不覆盖旧分段。
- 重连后查询在线列表、地图和当前轮排行榜，使用 `scores` 等可用信息补偿断连期间错过的成绩，并与已持久化事件去重。
- 对无法由排行榜恢复的 DNF、Warning、掉线顺序或命令回显建立“观察缺口”，不得猜测。
- 保存权威 Go 的 UTC 时间、原时限截止和接收窗口状态；进程重启后据此恢复剩余时间。检测到系统时钟跳变时进入事故复核。
- 自动核对没有发现观察缺口、身份冲突或不确定命令时，可经现场恢复确认继续原流程；否则保持暂停，等待裁判选择继续、修订或重赛。

### 12.5 裁判或服务器断连恢复

- MockClient 与服务器断连但后端仍运行时，持续保存本地现场、断连起止、当前尝试和最后事件偏移。
- 恢复连接后先重新获取玩家与排行榜快照，再恢复增量日志处理和自动调度。
- 后端中止期间服务器比赛可能继续，恢复时不能补发已经过期的公告、Ready 或 Go。
- 恢复得到的排行榜成绩保留“恢复查询”来源，若无法还原精确事件顺序则进入待复核。
- 比赛继续后所有新事件沿用原 `Competition`、`Stage` 和 `Attempt`；只有经过确认的重赛才创建新尝试。

## 13. 测试场景与日志材料

### 13.1 测试运行能力

- `player-behavior` 是普通测试入口：场景只包含玩家阵容和行为模型，轮次、计分、Ready、Go、换轮和结束来自当前比赛配置及裁判状态机。
- 每个内置行为场景至少 15 名玩家并声明固定随机种子。20 人小型综合沙盒为 8 普通、6 高手、3 低手、3 捣乱者；30 人大型沙盒为 12 普通、8 高手、6 低手、4 捣乱者。普通/高手完成时间、低手超时选择、捣乱者违规时刻由 `seed + 轮次 + 尝试 + 玩家 + 行为通道` 确定。
- 综合沙盒只带少量固定种子的短暂掉线/重连和明确 Warning 等可恢复故障。保护期崩溃、服务器断线、MockClient 退出和时钟跳变使用独立场景，按关卡及阶段相对触发；不提供独立的手动故障注入动作。
- `static-log` 只读打开完整 `.log`；`growing-log` 按字节偏移读取仍在增长的文件。
- 支持原速、倍速、逐事件、暂停、从头重置和跳转到下一次 Go。
- `static-log`、`growing-log` 和 `scripted-replay` 属于高级回放输入，可明确年份、时区、发令源、轮次、计分和预期事件；不出现在普通行为场景库。
- 测试运行复用工作模式的解析器、状态机和计分引擎，真实进程、网络和命令发送器替换为安全测试实现。
- 从头重放可生成事件/榜单哈希并比较确定性。

### 13.2 核心回归场景

默认产品旅程使用混合玩家行为场景，验证场景不含 Ready/Go、裁判自动或手动发令均可驱动玩家、尾部接收和换轮仍读取比赛配置。三轮混合 SR/HS 的逐事件材料保留为 `scripted-replay` 自动回归，不作为普通场景卡片。

其余行为使用单目标最小场景分别覆盖重连、Ready 掉线、稳定窗口、比赛中 cheat、重赛、命令不确定、服务恢复、修订和导出。cheat/Warning 的真实完赛证据必须保留但标为排除；超时只由状态机写入 DNF 结果，二者都不得伪造 MockClient `did not finish` 行。

### 13.3 历史参考材料

`test/fixtures/replay/2025-grandprix-sr1-13/` 仅用于了解真实日志格式、发现交错事件和辅助人工排查：

- 不进入默认 CI，不要求固定十三关结果，不作为发布门禁。
- 不从该材料向生产代码引入裁判名、关卡或代理发令特例。
- 从中发现的有效边界必须先提炼成脱离原日志的最小场景，再成为正式验收要求。
- 参考文件仍保持只读；分析前后可以校验大小、时间和 SHA-256。

### 13.3 源文件只读保证

- 完整回测日志读取前后记录大小、最后写入时间和 SHA-256。
- 回放、暂停、跳转和重置均不写源目录。
- 实际比赛增长日志按已提交字节偏移增量读取，并保持源文件只读。
- 稳定夹具组织在 `test/fixtures/replay/`；综合日志与人工维护的清单使用独立子目录保存。

### 13.4 测试夹具策略

- `2025 grandprix SR1-13 MockClient.log` 只作为非门禁参考材料，用于发现真实比赛中的日志格式和交错事件。
- 为单一行为建立更轻量、有针对性的最小日志夹具，例如：Go 前练习成绩、重连 ID 变化、最后计分名次衔接、Ready 截止、实时榜单基线、延时稳定窗口、比赛中开启 cheat、重赛和中断恢复。
- 每个夹具只保留验证目标需要的事件，明确比赛配置、期望标准事件和最终榜单，减少综合日志变化导致的脆弱断言。
- 解析器单元测试可直接构造日志行；跨事件状态机测试使用小型完整文件；综合日志只承担端到端回归。

## 14. 非功能要求

### 14.1 性能与可靠性

- 完整日志行出现后 500 ms 内进入标准事件流，1 秒内形成新榜单版本。
- 支持 30 名玩家、30 个轮次和持续 8 小时比赛。
- 日志解析、导出和归档不能阻塞状态机和命令回显处理。
- 计时不依赖前端连接或浏览器活动状态。
- 命令、原始事件和人工覆盖在服务异常退出后不丢失。
- 原始 Client 行按比赛持久化并通过统一查询接口提供；工作模式保存真实 MockClient 行，测试模式保存模拟玩家/裁判行，且模拟行应复用真实 MockClient 的时间前缀和已知事件句式，前端切页不得影响采集。

### 14.2 安全

- 固定监听 `127.0.0.1:32113`，拒绝未授权本机会话，不在端口占用时退回随机端口。
- 外部文本按数据处理，禁止用于 shell、SQL、模板代码或路径拼接。
- 可执行文件、日志和归档路径规范化，验证目标位于用户授权位置。
- 原始命令默认关闭，开启后限制长度和控制字符并完整审计。
- UUID、会话令牌和其他敏感配置不进入普通成绩导出。

### 14.3 可观测性

- 应用日志区分进程、解析、状态机、命令、API、存储和归档模块。
- 保存应用、适配器和解析器版本。
- 提供脱敏诊断包，默认不包含完整玩家聊天和敏感令牌。
- 所有事故和阻断具有机器可读代码和面向裁判的中文说明。

### 14.4 兼容性

- 支持仍受 Microsoft 支持的 Windows 10/11。
- 文件和内部文本使用 UTF-8；XLSX 使用 Open XML。
- 玩家名支持中文、英文、数字、下划线及日志样例中已有字符。
- MockClient 版本变化通过适配器和兼容性测试处理。

## 15. 后端测试与验收

### 15.1 单元测试

- 所有已知日志格式及未知/截断/ANSI/异常编码输入。
- 原始与自制地图、SR/HS、混合模式和模式省略时的上下文推断。
- 小型、大型、自定义计分和完整同分规则。
- 玩家重连、大小写变化、同名冲突和人工合并/拆分。
- 状态机合法/非法迁移、状态版本冲突和确认令牌失效。
- 工作模式只接受本机 MockClient 自身 ID 的 Go，其他客户端的 Go 仅记录且不创建尝试。
- 命令回显、分动作确认窗口、超时、不确定状态、逐条确认已执行/显式重发及幂等键；重发必须生成新审计且原记录保持不确定。
- 人工覆盖、撤销和榜单确定性。
- 比赛中未完赛玩家开启 cheat 自动 DNF，练习、完赛后开启和裁判全局开启不误判。
- 达到自适应最后计分名次后的下一轮调度、尾部成绩继续接收和实际 Ready 原子截止；小型值为 12、大型值为 15，并另含自定义配置测试。
- 每条有效完赛/DNF 生成榜单版本，以及首个完赛前锁定基线并实时计算排名变化。

### 15.2 集成测试

- 使用可控假 MockClient 验证启动参数、stdin、stdout、退出和重连。
- 正常自动流程按 T-60/T/T+5/T+10/T+15/T+20/确认后至少 10 秒完成 Notice、三次 Ready、`READY!`、关闭 cheat、倒计时、Go、计时和结算；回显延迟必须顺延后续步骤。
- 首次启动自动化先发布关卡与 Ready 时间并保留默认 3 分钟；一般暂停/阻断期间仍接收尾部成绩并触发时限，恢复后沿用原阶段和计划。
- `list` 的旧式列表头和实服客户端行加末尾汇总都能确认命令、排除旁观者并完成名单对账。
- 官图 `level N` 和自制图 `<完整 MD5> 0 <sr|hs>` 命令分别匹配实服的不带引号官图哈希回显，以及带引号的自制图哈希前缀或已注册地图名；自制图 Ready、Go、完赛、DNF 的唯一名称/前缀归属均有回归，歧义项不计分。
- 仅高级 `scripted-replay` 夹具可以显式声明历史发令来源；普通玩家行为场景不得声明发令。两者都不能硬编码历史特例或放宽工作模式的单一裁判校验。
- Go 写入成功但无回显时不创建尝试、不启动计时、不自动重试。
- 已达到最后计分名次后，在下一 Ready 实际开始前继续接收第 13 名及以后等零分完赛，并在 API、实时快照和浏览器排行榜中保留。
- Ready 阶段掉线会等待，重连后重新准备。
- 延时相关玩家稳定在线 15 秒后提前结束延时，再次掉线会重置稳定计时。
- 当前关 Go 后、下一关 Ready 前可直接“重赛本关”，无需先创建事故；确认后旧尝试永久保留但退出有效榜，完整 Ready/倒数重新执行并等待新 Go 创建尝试。
- 当前关成绩不可修订；进入下一关 Ready 后此前关卡可修订，结束/归档后全部可修订。确认和最终写入均重复校验；人工修订后继续接收自动成绩时榜单版本保持严格递增。
- 草稿、运行中、已结束和已归档比赛均可删除；进入复核在状态迁移事务内立即结束，不依赖读取快照触发。
- 服务崩溃重启后恢复原比赛、轮次、尝试、计时和成绩接收窗口，未决不可幂等命令进入不确定状态。
- MockClient 重连后通过排行榜查询补回可恢复成绩，对无法恢复的信息建立观察缺口。
- WebSocket 丢线、续传、序号缺口和快照恢复。
- 开发启动器在 `32113` 上识别并优雅停止旧项目实例；未知进程占用端口时拒绝误杀。

### 15.3 测试模式验收

- 三轮主场景和各单目标最小场景得到人工维护的预期事件、榜单和哈希。
- 正式 Go 前练习记录排除，通知文本时间不改变事件排序。
- 同一场景、配置和解析器版本重复运行得到相同哈希。
- 静态/增长日志读取不改变源文件大小、时间戳、哈希或既有字节。
- 测试模式不启动真实 MockClient、不联网、不发送真实命令，所有产物带测试标识。

### 15.4 导出与归档验收

- 页面、剪贴板 HTML/TSV、XLSX、CSV 来自同一共享表模型和固定榜单版本，浏览器测试逐格对比矩阵。
- XLSX 保留每关前三名颜色、DNF 删除线、排除样式和冻结表头；超过 Z 列仍使用合法 Excel 列引用。
- HTML/TSV 下载格式被拒绝；新归档只包含 XLSX、CSV 两种成绩文件。
- 归档包含清单规定内容且所有哈希可复算。
- 已归档版本不可覆盖，复核产生新版本。

### 15.5 性能与长时测试

- 模拟 30 名玩家、30 轮、8 小时事件流，不丢事件、不重复计分。
- 大日志跟随、筛选、导出和归档期间，关键命令回显处理仍满足时延要求。
- 模拟休眠/唤醒和系统时间变化，确保不补发过期 Go。

## 16. 后端实施顺序

1. 领域模型、SQLite、配置版本、原始事件存储和迁移框架。
2. 日志读取器、版本化解析器、标准事件、测试场景运行器和最小回归夹具。
3. 玩家身份、尝试切分、SR/HS 计分、覆盖和榜单版本。
4. HTTP/WebSocket、本机会话、状态版本和幂等动作。
5. 工作模式 MockClient 进程适配器、命令队列和回显。
6. 自动状态机、调度、阻断、掉线/崩溃事故和重赛确认。
7. 导出、归档、崩溃恢复、诊断和长时可靠性测试。
8. 报名映射、别名、黑白名单及只读观察者等扩展模型。

每一阶段必须复用同一事件模型和计分引擎，避免工作模式、测试模式和导出产生不同规则实现。

## 17. 默认假设

- 本机后端固定监听 `127.0.0.1:32113`。
- 默认裁判名为 `ContestConsole`，MockClient 必须自动以 `*ContestConsole` 旁观登录；工作模式只认可本机 MockClient 自身连接 ID，测试模式权威发令由裁判状态机生成，玩家行为场景不得定义裁判发令。
- 新建比赛默认工作模式；测试模式由裁判主动选择，且创建后不可切换。
- 比赛类型默认小型，默认服务器为不带端口的 `1.bmmo.win`。
- 正常自动 Go 无需逐次确认；手动 Go 和比赛中重赛需要确认。
- 赛前等待上限 5 分钟、重连稳定窗口 15 秒、固定发令时间轴和起跑保护窗口 15 秒。
- 内置计分表的最后计分名次为小型 12、大型 15；自定义方案取最后一个非零得分对应名次。达到该名次后立即按默认 3 分钟轮间休息安排下一 Ready，不等待原关卡剩余时限；旧窗口在下一 Ready 或原时限先到时关闭。
- 首版按游戏内玩家 ID 从 login/disconnect/`list` 自动登记，数字连接 ID 仅作历史记录；显示名映射不参与成绩归属。
- 测试输入日志和工作模式增长日志始终只读，派生数据库、缓存、导出和归档写入按模式隔离的独立目录。

## 18. 开发澄清原则

开发过程中若发现规则语义、默认值、协议能力、异常恢复、命令确认、数据迁移或验收结果存在多种合理解释，必须先向用户确认，再更新需求文档、测试和实现；不得静默采用未经确认的假设。
